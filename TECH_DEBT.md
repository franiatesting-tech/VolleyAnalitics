## Synthetic match data written to both the ontology and a JSON blob (revised scope, no longer expected to be fully paid down pre-Phase-5)
- Introduced: 2026-08-28, Phase 1 (ROADMAP.md), see ADR-002. **Partially paid down 2026-08-28, Phase 2, see ADR-004** — the real Event Log ontology now exists and `process_demo_match` persists into it (`persist_synthetic_match`). **Scope refined 2026-08-29, Phase 3** — see below; this is now a *deliberate, longer-lived coexistence*, not a stopgap waiting on frontend migration.
- What's still shortcut, and why it's staying: Phase 3's Match Analysis / Rally Explorer UI (`apps/web/src/components/match-analysis.tsx`, `rallies/rally-explorer.tsx`) now reads sets/rallies/statistics/actions entirely from the real ontology endpoints (`/matches/{id}/sets`, `/rallies`, `/rallies/{id}/actions`, `/statistics`) — every number a coach sees is traceable to real `Action`/`Outcome`/`Rally` rows. The one thing still read from `GET /matches/{id}/result` (the JSON blob) is per-rally **continuous position time series** (`player_positions`/`ball_positions`) for the rally replay animation. This is *not* an oversight: `BallObservation`/`PlayerObservation` are schema-designed for genuine CV-model output (`model_run_id` NOT NULL/CASCADE from a real detection run, `video_id` NOT NULL — see ONTOLOGY.md) and stuffing procedurally-generated synthetic positions into them would misrepresent them as real detections, violating the Prediction/GroundTruth separation this project treats as non-negotiable (CLAUDE.md's Traceability section). So the blob's replay-position role has no ontology-table home until real per-frame observations exist. Real `Rally` rows are paired to their synthetic replay counterpart by `(set index, index_in_set)` — **never by id**, since `persist_synthetic_match` mints fresh UUIDs and does not preserve the generator's own in-memory ids (see `apps/web/src/lib/ontology.ts`'s `pairRallyWithSynthetic`, and the same file's `deriveTeamSides`, which also anchors on this pairing since `MatchOut` never exposes `home_team_id`/`away_team_id` — see the new entry below).
- Blast radius: unchanged for the blob's discrete fields (must never be reused for real match data — no query/index support, no per-event correction; the frontend no longer reads any of them). The position-time-series fields are synthetic-only by construction and Phase 3's replay UI labels them honestly ("Video not available yet — synthetic reconstruction shown").
- Must be paid down: **not at a fixed phase boundary anymore** — the condition is "a real per-frame position pipeline exists" (Phase 5's `BallObservation`/`PlayerObservation` population, Phase 6+ for pose-derived player tracks). At that point, Rally Explorer's replay source should switch from the JSON blob to querying real observations for videoed matches, keeping the synthetic blob path only for matches that were never processed by a real pipeline (if that demo path is even kept by then). Until then, `ProcessingJob.result_data` and `GET /matches/{id}/result` stay — removing them now would delete the only source of replay data with nothing to replace it.

## `services/api` 500s on every DB route when run directly on a Windows host (not via Docker)
- Introduced: unknown (pre-existing since Phase 1, first noticed 2026-08-29 during Phase 3 verification)
- psycopg's async driver raises `InterfaceError: Psycopg cannot use the 'ProactorEventLoop'` on any route touching the async DB session, when `uvicorn volley_api.main:app` is run directly on Windows (not inside Docker). A `sys.platform == "win32"` guard setting `asyncio.set_event_loop_policy(WindowsSelectorEventLoopPolicy())` was tried in `main.py` and reverted after confirming it doesn't work: uvicorn's CLI (`uvicorn app:app`) creates and starts its event loop *before* importing the ASGI app string, so by the time `main.py`'s module-level code runs, the wrong-policy loop already exists — the module-level guard is provably too late, not a partial fix. A real fix needs a custom entrypoint (e.g. `python -m volley_api` calling `uvicorn.run(...)` programmatically after setting the policy, in a script that runs *before* uvicorn's own loop creation) — not attempted, since this session's actual verification worked around it entirely by using the already-built Docker images for `api`/`worker` instead (Linux containers never hit this).
- Blast radius: blocks bare-metal Windows host development of `services/api` specifically (not `apps/web`, not `services/worker`, which uses Celery's own sync-friendly execution model and isn't affected). Zero impact on the project's actual supported dev path (`docker compose`) or CI (`ubuntu-latest`) — both run Linux, where this class of error can't occur.
- Must be paid down: before recommending bare-Windows-host (non-Docker) development of `services/api` as a supported workflow in any onboarding doc. Until then, Windows contributors should run `services/api` via `docker compose up api` rather than `uv run uvicorn` directly.

## `MatchOut` team-id gap (paid down 2026-08-29, Phase 3 — kept for history)
- Introduced: 2026-08-29, Phase 3. **Fixed 2026-08-29**, same phase, after independent architecture review both found the gap and caught that the first attempted fix description (just adding the columns to `MatchOut`) was factually wrong — `persist_synthetic_match` never actually wrote `Match.home_team_id`/`away_team_id`, so that alone would have shipped `null, null` forever.
- What was actually shortcut, historically: `volley_domain.models.Match` had real, nullable `home_team_id`/`away_team_id` FK columns, but nothing ever populated them, and `volley_domain.schemas.MatchOut` never returned them. `apps/web/src/lib/ontology.ts`'s `deriveTeamSides` worked around this by anchoring on the synthetic JSON blob's `SyntheticRally.serving_team`, paired to its real `Rally` counterpart by `(set index, index_in_set)`.
- **The real fix, verified end-to-end (not just schema-deep):** `persist_synthetic_match` (`packages/domain-py/src/volley_domain/synthetic/persistence.py`) now sets `match.home_team_id`/`away_team_id` on the real, session-tracked `Match` row (raises if the row is missing, rather than the earlier draft's silent no-op) — new test `test_persist_synthetic_match_links_match_to_its_home_and_away_teams` asserts this against a committed+refreshed row, not an in-memory object. `MatchOut` exposes both fields (nullable). `deriveTeamSides` is now a 3-tier fallback: real `MatchOut` ids (authoritative) → derive from `MatchSet.winner_team_id` + points using **rally** data to discover both team ids (`collectTwoTeamIds`, not set winners alone — an earlier design using only set winners would have failed on any ordinary 3-0 sweep, caught before it shipped) → the original blob-pairing, kept as a last resort for matches persisted before this fix existed.
- Blast radius: none currently outstanding — every match created going forward gets tier 1 for free; every match already persisted still resolves correctly via tier 2/3.
- Nothing left to pay down for this entry specifically. Two small residual items tracked separately, not urgent: no API-level test asserts `home_team_id` appears in the actual `/matches/{id}` response payload after demo processing (schema-level and persistence-level are each tested, the seam between them isn't); tier 2's code comment should say "uses the first decided set found" rather than implying corroboration across all sets, since that's what the code actually does.

## "Blocked attack" statistic and `BlockStats.block_kills` were both structurally unreachable on synthetic data -- fixed 2026-08-30
- Introduced: 2026-08-28, Phase 2, see ADR-004 "Independent review findings". `block_kills` additionally surfaced in the UI 2026-08-29, Phase 3 (`stats/statistics-dashboard.tsx`'s "Block kills" tile), read as "neither team ever got a kill block" rather than "not modeled yet" -- found by independent qa-release-engineer review. **Both fixed together 2026-08-30**, since they're the two symptoms of the same root cause: the generator never produced a rally ending in an opposing block stuffing an attack.
- What was wrong: `compute_attack_stats`'s `blocked` count inferred a blocked attack from an attack-error immediately followed by an opposing block action, but the generator's last-exchange logic returned immediately on any attack error with no block action ever added -- so the adjacency pattern the heuristic depended on never occurred. Separately, `_build_action_chain`'s block sub-path hardcoded `def_outcome = "error" if def_type == "block" else "continue"`, so a block's outcome was never `"point"`, and `compute_block_stats`'s `block_kills` (which counts blocks with outcome `"point"`) was guaranteed to be 0. Both formulas were individually correct and individually unit-tested with hand-built fixtures -- neither test used the real generator, so neither gap was caught until independent review traced the generator's own logic.
- Fix, done as recommended by both entries' own "more correct design" note rather than papering over the generator gap alone: (1) `Outcome.detail` (already existed on the ORM model, unused until now) is threaded end-to-end -- `SyntheticAction.detail` -> `ActionRecord.outcome_detail` -> `Outcome.detail` via `persist_synthetic_match`; `compute_attack_stats` now trusts `outcome_detail == "blocked"` as its primary signal and only falls back to the old adjacency heuristic when `outcome_detail` is `None` (so older/unlabeled data still gets a best-effort count, and an explicit non-"blocked" label always overrides the heuristic -- both behaviors covered by dedicated tests). (2) The generator's last-exchange "attack error" branch now has a `stuffed = rng.random() < 0.3` sub-path: `attack(outcome="error", detail="blocked")` immediately followed by `block(outcome="point")` from the opposing team, matching standard scorekeeping convention (DataVolley/NCAA/SDHSAA credit both the hitter's attack error and the blocker's block kill for the same stuff). Verified measured, not assumed: `test_blocked_attacks_and_block_kills_are_actually_produced` confirms both statistics are nonzero across 20 seeds and that every occurrence is internally consistent (adjacent actions, opposite teams, rally's own `point_winner` agrees); `test_persist_synthetic_match_writes_outcome_detail_for_blocked_attacks` confirms `Outcome.detail` round-trips through real persistence.
- Blast radius: none outstanding. Both statistics now read real, nonzero, internally-consistent numbers on synthetic/demo data; the UI's "Block kills" tile no longer misrepresents an unmodeled field as a real zero.
- Nothing left to pay down.

## `persist_synthetic_match` creates fresh Season/Team/Player/Roster rows on every call, no get-or-create -- fixed 2026-08-30
- Introduced: 2026-08-28, Phase 2, see ADR-004 "Independent architecture review findings" (S1). **Fixed 2026-08-30**, exactly as this entry's own fix recommendation specified.
- What was wrong: every call to `persist_synthetic_match` (one per synthetic-demo generation) inserted brand-new `Season`/`Team`/`Player`/`Roster` rows even when a team of the same name already existed from a prior demo run.
- Fix: `persist_synthetic_match` now calls `_get_or_create_season`/`_get_or_create_team`/`_get_or_create_player`/`_get_or_create_roster` (new helpers in `persistence.py`), keyed on `(organization_id, name)` for Season/Team, `(organization_id, first_name, last_name)` for Player (sound specifically because this generator's names are deterministic per team-name + roster index, not per seed -- documented on the helper as never to be reused for real players, who can share a name), and `(team_id, player_id, season_id)` for Roster (the actual membership identity -- `uq_roster_team_season_jersey` alone can't catch a duplicate here, since a re-run's freshly-randomized jersey number for the same player differs from the prior run's). On reuse, the original row's data (e.g. jersey_number) is kept, not overwritten -- get-or-create means "reuse," not "upsert." Multi-tenancy is preserved: a different `organization_id` never dedups against another tenant's rows. Verified with three new tests: repeated demo runs for the same org/team names produce exactly 2 Teams / 1 Season / 14 Players / 14 Rosters (not 4/2/28/28) regardless of seed; a second org's identical team names get their own independent rows; a player's jersey number from the first run survives a second run untouched.
- Blast radius: none outstanding.
- Nothing left to pay down.

## Local-upload route buffers the request body in memory -- fixed 2026-08-30 (revised again same day, this entry now closed)
- Introduced: 2026-08-29, Phase 4 (`services/api/src/volley_api/api/routes/videos.py`'s `local_upload`). **Fixed 2026-08-30** after independent security review demonstrated the original "deliberate, low blast radius" framing was wrong -- a 25 MiB unauthenticated-by-JWT PUT succeeded with no size check at all, an unbounded memory/disk-fill primitive, not just a theoretical one. An earlier same-day revision of this entry described a Python-list-buffered intermediate fix (up to ~512 MiB held in memory); that description is now stale -- the actual current code is stronger, confirmed by a second independent re-confirmation review reading the live source.
- What the code actually does now: chunks stream into a `tempfile.SpooledTemporaryFile(max_size=8 MiB)`, so peak process memory is bounded at ~8 MiB regardless of upload size -- anything past that spills to a real temp file on disk, never held in a Python list. The streaming loop aborts with 413 as soon as the running total exceeds `min(local_upload_max_bytes, max_video_upload_bytes)` (2 GiB / 20 GiB respectively), and a `Content-Length` header over that limit is rejected before any bytes are read at all. The spooled content is then read back out and handed to `write_object` as a chunk generator, not a single in-memory blob. Same pass also fixed: the route requires the target key to not already exist (`object_exists` check) before accepting a write, closing a separate token-replay/content-swap issue.
- Blast radius: none in production (route is unreachable when `STORAGE_BACKEND=r2`, and `Settings._local_storage_cannot_reach_production` refuses to even start with `STORAGE_BACKEND=local` outside dev/test). Local dev memory usage is bounded at ~8 MiB regardless of caller behavior; disk usage is bounded by the 2 GiB cap.
- Must be paid down: nothing outstanding for this specific entry. If this route is ever repurposed as more than a local-dev/test stand-in (not currently planned), the 2 GiB cap would need reconsidering for real multi-GB video.

## `ingest_video`'s duplicate-content handling rejects rather than merges
- Introduced: 2026-08-29, Phase 4 (`services/worker/src/volley_worker/ingest.py`)
- When a newly-ingested video's SHA-256 matches an existing `Video` row in the same organization, the new upload is marked `FAILED` with a descriptive error (`"Duplicate content: identical video_hash already exists as video <id>..."`) rather than being linked/merged to the existing row. A real product might instead offer to reuse the existing `Video` (e.g. the user re-uploaded the same file by mistake) rather than presenting a bare failure.
- Blast radius: low -- correct, safe behavior (never silently creates a second `Video` row for identical content, never silently overwrites), just not the most user-friendly resolution. Verified via `services/worker/tests/test_ingest.py::test_duplicate_hash_within_org_fails_without_overwriting_the_original` and its cross-org counterpart (confirming org isolation applies to content-addressing too).
- Must be paid down: before duplicate-upload is a real user-facing flow (Phase 7+, once real client uploads happen) -- likely a product/UX decision (auto-link vs. ask the user), not purely technical, so flag for `architecture-lead`/product input rather than guessing the UX here.

## `videos.video_hash` going nullable was a real ADR-worthy decision, recorded only in a code comment
- Introduced: 2026-08-29, Phase 4 (migration `0003`). Flagged by independent architecture review 2026-08-30 -- not fixed this pass.
- `video_hash` is CLAUDE.md's Traceability section's named video identity column and the first term of the `video_hash + pipeline_version + config_hash` idempotency key, and Phase 4 loosened it from `NOT NULL` to nullable. The reasoning (a `Video` row must exist before hashing is possible, to give the client a stable `video_id` to poll) is sound and was independently re-verified as the right call -- but it lives only in `ontology.py`'s `Video.video_hash` docstring and the migration's own docstring, not in `docs/domain/ONTOLOGY.md` (which still describes `Video` as "hash, duration, fps, codec, upload metadata" with no mention of the upload lifecycle or that the hash can be absent) or a dedicated ADR. `uq_video_org_hash`'s behavior under NULLs (SQL treats every NULL as distinct, so concurrent un-hashed uploads never collide) is correct but also undocumented outside the code.
- Blast radius: low today, grows as more contributors touch `Video`/ingest without the full "why nullable" context readily available in the docs a future contributor would actually check first.
- Must be paid down: write ADR-005 (or amend ADR-004) documenting this decision properly, and update `ONTOLOGY.md`'s `Video` entity description to reflect the real `uploaded -> validating -> ready/failed` lifecycle and the hash's nullable window. Cheap, should happen before Phase 5 builds more on top of this table.

## A `Video` row could get stuck in VALIDATING forever if enqueueing its ingest task failed after the status was already committed -- fixed 2026-08-30
- Introduced: 2026-08-29, Phase 4. Found and fixed 2026-08-30, independent architecture review (live-traced, not hypothetical): `complete_video_upload` committed `status = VALIDATING` *before* calling `enqueue_ingest_video`; if the enqueue call then raised (e.g. Valkey unreachable), the row was left at `VALIDATING` with no task in flight and no error -- and `VALIDATING` is one of the two statuses this same route's own idempotency guard short-circuits on, so a client retry would silently no-op instead of actually retrying.
- Fix: the enqueue call is now wrapped in its own try/except; on failure the row is reverted to `FAILED` (not in the idempotency-guard tuple) with a descriptive error, so a client retry genuinely re-enqueues. The route also now checks the object actually exists in storage before flipping to `VALIDATING` at all, closing a related "enqueue a task that will always fail because nothing was ever uploaded" gap the same review found.
- Blast radius: none outstanding for this specific bug. No test yet asserts the enqueue-failure-then-revert path specifically (would need mocking `enqueue_ingest_video` to raise) -- worth adding before this route sees real traffic.
- Must be paid down: add `test_complete_upload_reverts_to_failed_when_enqueue_raises` before Phase 5/6 puts real load through this endpoint.

## `StorageAdapter` is missing capabilities Phase 5 will need: backend-agnostic write, signed download, multipart
- Introduced: 2026-08-29, Phase 4. Flagged by independent architecture review 2026-08-30 -- not fixed this pass (deliberately not speculative additions without a real caller yet, per this project's own "no abstractions before they're needed" principle, but the *specific* gaps below are named requirements, not speculation).
- Three of `StorageAdapter`'s six abstract methods (`object_exists`, `stat`, `delete`) have no caller anywhere in the codebase yet, while three real, already-named needs are missing: (1) no backend-agnostic *write* -- `write_object` exists only on `LocalFilesystemStorageAdapter`, not on the ABC or `R2StorageAdapter`, so the worker has no way to upload a generated proxy video (`VideoAssetKind.PROXY`, which already exists in the ontology) once Phase 5 needs to produce one; (2) no signed *download* target -- `DATA_FLOW.md`'s "bytes never transit FastAPI" rule needs the same treatment on the read path Phase 3's video-player slot is already waiting on; (3) `create_signed_upload` issues a single presigned PUT (5 GiB cap on S3/R2, no resume), while CLAUDE.md's Storage fixed decision explicitly names "signed/multipart URLs" as the requirement.
- Blast radius: none today (nothing calls the missing methods yet since no real video/proxy pipeline exists). Becomes real the moment Phase 5 needs to write a proxy or Phase 3's video player needs a real signed GET.
- Must be paid down: before Phase 5 needs proxy-video writes, or before any real match video large enough to exceed 5 GiB is expected -- add `write_object`/a signed-download method to the ABC (both backends), and switch `create_signed_upload` to R2/S3 multipart for uploads above a size threshold.

## Ingest creates no `PipelineRun`/`ModelRun` row, so `Video.fps`/`width`/`height`/`codec` carry no provenance -- fixed 2026-08-30
- Introduced: 2026-08-29, Phase 4. Flagged by independent architecture review 2026-08-30. **Fixed 2026-08-30**, before real annotation work begins on `golden-v0` (this was the entry's own stated pay-down condition, and CVAT tasks for that dataset now exist).
- What was wrong: `PipelineRun`'s own docstring calls it "the `video_hash + pipeline_version + config_hash` idempotency key from DATA_FLOW.md, as a real row," but `ingest_video` was keyed solely by `video_id` and never created one -- so there was no persisted record of which ffmpeg build, code commit, or ingest config produced any given `Video`'s `fps`/`width`/`height`/`codec`, and per the PTS-mapping fix above, `fps` is the denominator every downstream ground-truth timestamp depends on.

## `leakage_safe_split` reshuffles most of an existing split when the dataset grows -- fixed 2026-08-30
- Introduced: 2026-08-29, Phase 4 (`packages/domain-py/src/volley_domain/dataset_split.py`). Found and reproduced live by independent architecture review 2026-08-30. **Fixed 2026-08-30**, before `golden-v0` needed to grow for the first time (it currently holds one frozen split from a single `split_cli` call, so nothing needed re-freezing).
- What was wrong: the split is deterministic for a *fixed* inventory (its own docstring's claim), but assignment is a greedy max-deficit fill over a hash-determined ordering, so adding new videos to a growing dataset perturbs the cumulative fill and cascades: verified directly (10 videos, seed=42, 60/20/20 split, then add 2 more videos with the same seed) that 8 of the original 10 videos get reassigned to a different split, including 2 videos moving from `test` into `train`. `detect_cross_split_group_leakage` did not catch this -- it detects a group spanning multiple splits in one snapshot, not a video changing splits between two versions of the dataset.

## `packages/contracts/node_modules` symlinks break inside Docker containers when `pnpm install` is run from the Windows host
- Introduced: unknown (present since the workspace was first set up); found while verifying the video-detection frontend in the browser -- every page failed to compile with `Module not found: Can't resolve 'openapi-fetch'`.
- Docker Desktop's 9p filesystem driver represents `packages/contracts` (bind-mounted into both `api`/`web` containers) with `symlinkroot=/mnt/host/` -- a WSL2-side remapping trick. A `pnpm install` run directly on the Windows host produces symlinks like `openapi-fetch -> /mnt/host/c/Users/.../node_modules/.pnpm/openapi-fetch@.../node_modules/openapi-fetch`, which only resolve correctly through that specific 9p driver path, not as a plain absolute path from inside a container's own mount namespace (confirmed directly: `ls /mnt/host/c/...` from inside the `web` container fails with "No such file or directory", since no container actually bind-mounts a generic `/mnt/host`). Any package whose `node_modules` symlinks were last written by a host-side `pnpm install` will silently fail to resolve inside Docker, and pnpm's own "already up to date" check doesn't notice the symlinks are broken (it trusts a state marker, not each link's actual resolvability). Worked around this session by deleting the three broken symlinks (`openapi-fetch`/`openapi-typescript`/`typescript`) and manually recreating them pointing at the container's own `/workspace/node_modules/.pnpm/...` store paths, then restarting the `web` container to clear Turbopack's cached compile failure.
- Blast radius: any contributor who runs `pnpm install` on the Windows host (rather than inside a container, e.g. `docker compose exec web pnpm install`) after adding/updating a dependency in a container-bind-mounted workspace package will silently re-break this exact symlink, and the breakage won't surface until something actually imports that package inside a container.
- Must be paid down: not urgent to fix structurally (workaround is a one-line `docker compose exec web pnpm install` instead of a host-side `pnpm install`), but worth a one-line note in a contributor-facing doc (README or a Windows-dev-setup note) once one exists, so this doesn't cost someone else the same debugging cycle. Consider instead whether the affected workspace packages could run `pnpm install` as part of each container's own startup/entrypoint, which would make this class of drift self-healing.
