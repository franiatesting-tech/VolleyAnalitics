# ADR-004: Volleyball Domain Ontology, Statistics Engine, and Lineage

- **Status:** Accepted
- **Date:** 2026-08-28
- **Deciders:** Claude Code acting as architecture-lead, per ROADMAP.md Phase 2
- **Supersedes:** none; extends ADR-002's schema (`packages/domain-py`) with the real volleyball ontology ADR-002 explicitly deferred

## Context

Phase 1 (ADR-002) shipped `Match`/`ProcessingJob` and a JSON-blob synthetic-match result, explicitly flagged in `TECH_DEBT.md` as needing replacement once "Phase 2's real Event Log ontology lands." This ADR is that landing: 21 new tables (`Season`/`Competition`/`Team`/`Player`/`Roster`/`Lineup`/`LineupPlayer`/`Rotation`/`MatchSet`/`Rally`/`Phase`/`Action`/`Outcome`/`Video`/`VideoAsset`/`PipelineRun`/`ModelRun`/`BallObservation`/`PlayerObservation`/`HumanCorrection`/`ReviewedLabel`), a pure statistics engine, a normalized coordinate system, a lineage helper, and an append-only correction service. Full entity documentation and the ER diagram live in `docs/domain/ONTOLOGY.md` — this ADR records the decisions and trade-offs, not the schema itself.

## Decisions

### No generic `Prediction` table

Considered and rejected. `Action`, `Outcome`, `BallObservation`, and `PlayerObservation` each carry their own provenance (`model_run_id`, `confidence`) directly rather than pointing at a shared polymorphic wrapper. A generic table would require every consumer to interpret an untyped JSON value and adds indirection with no current query benefit. Revisit only if a real "list all unreviewed predictions of any kind" feature needs a unified surface a `UNION` across the typed tables can't serve.

### `CourtPosition` is a value type (`volley_domain.court`), not a table

Normalized `(x, y)` coordinates are plain columns on `Action`/`BallObservation`/`PlayerObservation`. The court *calibration* that gives those coordinates real-world meaning (homography, confidence) gets its own table in Phase 5 (`ml/court`) once something actually produces it — deliberately not modeled yet, per "no dejar TODOs silenciosos" (this is a documented deferral, not a forgotten one). An earlier draft of this ADR said "Phase 3" here, which is the frontend design-system phase, not the phase that actually produces court calibration data — caught by independent architecture review.

### `packages/domain-py` split into `base.py` / `models.py` / `ontology.py`

`base.py` holds the shared `Base`/id/timestamp helpers; `models.py` keeps Phase 1's `Match`/`ProcessingJob`; `ontology.py` holds everything new. `volley_domain/__init__.py` eagerly imports both model modules so every table registers on `Base.metadata` before Alembic or `create_all` inspects it — the alternative (each caller remembering to import the right submodule) is exactly the kind of thing that goes silently wrong months later.

### `PipelineRun.video_id` is nullable — one deliberate exception

A real pipeline run always has a source video; `video_id` should be `NOT NULL`. But `ModelRunStage.SYNTHETIC` runs (the Phase 1/2 demo generator) have no video, and creating a placeholder `Video` row to satisfy a constraint would misrepresent one as existing — worse than a nullable column. This was caught mid-implementation (see "what was verified" below) rather than designed upfront; application code must not create a non-`SYNTHETIC` `PipelineRun` with a null `video_id`, and nothing currently enforces that at the DB level (a `CHECK` constraint tying `video_id IS NOT NULL OR stage = 'synthetic'` would need a cross-table constraint Postgres can't express directly — worth a partial index or application-level check when real pipeline runs exist in Phase 5; not needed yet since only synthetic runs exist).

### Migration 0002 is frozen, hand-owned DDL — not read from live metadata (revised after independent review)

The first draft of this migration iterated `Base.metadata.sorted_tables` and called `Table.create()`/`Table.drop()` directly against the live ORM metadata at migration-run time, on the theory that 21 tables with ~40 foreign keys was past the point where hand-transcription is reliably correct. An independent architecture review rejected that rationale on inspection: a migration file's job is to be a frozen, dated snapshot of "what revision 0002 does," and reading live metadata means that snapshot silently changes if `ontology.py` is ever edited later — a column rename six months from now would retroactively rewrite what this already-applied revision meant, with no new revision recorded and no way to reconstruct what actually ran against a given database. The transcription-accuracy concern was real, but the fix wasn't "read the metadata forever," it was "generate the DDL from metadata once, then freeze the result as plain text" — exactly what `alembic revision --autogenerate` would hand you if a live database had been available to diff against. That's what this migration now does: the `op.create_table()`/`op.create_index()` calls were generated once from `ontology.py`'s metadata via a one-off script, reviewed by hand, and committed as static code with no runtime dependency on `volley_domain` at all. Verified via `alembic upgrade head --sql` and `alembic downgrade head:0001 --sql` (offline mode, no live Postgres available this session — see PROJECT_STATUS.md) to confirm both directions produce valid, FK-order-correct DDL.

### The synthetic generator now persists into the real ontology, and the JSON blob stays too — for now

`services/worker`'s `process_demo_match` task now calls `persist_synthetic_match` (writing real `Team`/`Roster`/`MatchSet`/`Rally`/`Phase`/`Action`/`Outcome`/`PipelineRun`/`ModelRun` rows) *and* still writes the Phase 1 JSON blob to `ProcessingJob.result_data`. This is deliberate, not an oversight: `apps/web`'s already-shipped, already-tested Match Detail page reads the JSON blob, and migrating that read path is a UI change out of this ADR's scope (data model + engine + lineage, not the frontend — that's Phase 3's Match Analysis work). Both are written inside one transaction (see `volley_worker/tasks.py`) so a failure partway through never leaves inconsistent state between them, and a Celery redelivery is safe (verified by test — see below) because the task's top-level "already `COMPLETED`" check gates the ontology-persistence call too, even though `persist_synthetic_match` itself has no dedup check of its own.

**Consequence, tracked in `TECH_DEBT.md`:** the JSON blob is now genuinely redundant with the ontology tables for anything the ontology can already answer. Removing it (and switching the frontend to the new `/matches/{id}/sets`, `/rallies`, `/statistics` endpoints) is real, scoped follow-up work, not indefinite dual-maintenance.

### Statistics engine formulas — verified, not assumed

Attack efficiency `(kills − errors) / total_attempts` was checked against SDHSAA's and the WIAA/NCAA worksheet's published conventions before implementing, including the exact 20/5/30 → 0.50 worked example (now a test case). Reception rating is explicitly configurable (`ReceptionRatingScale`, default 0–3 per coachingvb.com's documented convention) rather than hard-coded, since sources confirm real programs use 0–3, 0–4, or letter-grade scales. See `docs/domain/ONTOLOGY.md`'s "Statistics engine" section for citations.

### `AttackStats.takeoff_position_counts` — renamed from "direction," per independent review

Originally shipped as `direction_counts`, bucketing the attacker's own recorded position (left/middle/right thirds) rather than a separately-tracked ball-landing spot. An independent domain review (see "Independent review findings" below) correctly pushed back on the docstring caveat as insufficient: "attack direction" is an unambiguous term to a coach (shot placement — line vs. cross-court), and a UI or export displaying "Attack Direction: 34% left…" would read as exactly that even with a caveat buried in code. Renamed to `takeoff_position_counts`, which can't be misread the same way. Still redundant with `zone_counts` today (both derived from the same coordinate) until real ball-landing data exists to make it a genuinely different signal — that redundancy is fine to ship, the mislabeling wasn't.

## Independent review findings (addressed 2026-08-28)

An independent volleyball-domain-analyst review found real, checkable bugs — not judgment calls — that a self-review missed:

1. **A real FIVB Rule 9.3 violation baked into the synthetic generator.** The non-terminal rally-exchange branch added a standalone `"transition"` action after every dig, so a team's contacts across two consecutive loop iterations were dig → transition → set → attack — four consecutive same-team touches, one more than the legal maximum of three. Confirmed by tracing the control flow directly (not just trusting the review): fixed by removing the standalone transition action (the dig is now that team's first touch of the next possession; their following set+attack are touches two and three). A new test (`test_no_team_ever_makes_more_than_three_consecutive_contacts`, checked across 30 seeds) exists specifically so this class of regression can't ship silently again — no test had checked contact-count legality before.
2. **`tip` actions were silently excluded from all attack statistics.** `compute_attack_stats` filtered on `action_type == "attack"` only; `ActionType.TIP` exists as a sibling type that never got merged in, so a team's tip kills/errors vanished from kills/errors/efficiency/zone counts entirely — no error, just a silent undercount. Fixed: `attack` and `tip` are now both treated as attack-like throughout (`_ATTACK_LIKE_ACTION_TYPES`), including in setter distribution's "was this set followed by an attack" check, which had the same gap.
3. **The `blocked` attack-error heuristic is real but was never exercised.** The reviewer traced the generator and found it never actually produces an attack-error-immediately-followed-by-opposing-block sequence (an attack error ends the rally immediately) — so `blocked` was always 0 on synthetic data despite a passing unit test (which used hand-built fixtures, not the real generator). Not fixed in this pass — a proper fix needs either the generator to produce real blocked sequences or `Outcome.detail`-based labeling instead of adjacency inference. Documented honestly in the engine's docstring and tracked in `TECH_DEBT.md` rather than silently left as an apparently-working stat.
4. **Phase-type vocabulary doesn't match formal coaching terminology.** `PhaseType.SERVE/RECEPTION/TRANSITION` is a defensible engineering proxy for Complex I / Complex II possession grouping, but a coach with formal training expects that vocabulary, not these labels — noted in `docs/domain/ONTOLOGY.md` as a documentation gap to close, not a schema change.
5. **Libero modeling is adequate for today's stats but insufficient for future rotation-legality validation.** `Roster.is_libero` + `LineupPlayer.is_libero_for_set` (two booleans) is enough for descriptive box-score stats (nothing in the engine currently branches on libero status), but can't reconstruct real libero substitution mechanics (swap-partner link, back-row-only restriction, serve eligibility). The reviewer explicitly declined to assert the exact current federation-specific libero rules rather than guess — correctly, per this project's own research-first principle. No schema change made; flagged as a real gap to close before any rotation-legality validation is built (Phase 6+), not before.

Everything else the review checked — attack efficiency formula, sideout/breakpoint % definitions, reception rating scale/threshold, court zone numbering (1–6 counter-clockwise from back-right) — was independently confirmed correct.

## Independent architecture review findings (addressed 2026-08-28)

A separate independent architecture-lead review, run specifically to check cross-cutting soundness (not volleyball-rule correctness), concluded the first draft of Phase 2 was "not yet sound" and found four blocking bugs plus four should-fix gaps:

**Blocking, all fixed:**

1. **Away-team zone attribution was silently wrong.** `synthetic/generator.py` called `zone_anchor(zone, team)`, which mirrors zone 1↔4 etc. for the away team, and then wrote the *mirrored* zone straight into `Action.court_x`/`court_y` — meaning an away-team zone-1 serve was persisted at the coordinates of zone 4. Reproduced directly (not just trusted): away zone-1 serves really did report as zone 4 before the fix. Mirroring is legitimately a *rendering* concern (drawing both teams on one shared visual court) per `court.py`'s own docstring, not a fact about how a single team's own action should be stored — every team's own actions must be recorded in its own attacking frame, never pre-mirrored. Fixed by removing all team-based mirroring from the generator; both teams now use the same unmirrored `ZONE_ANCHORS` lookup. This was the most severe of the four bugs — it would have silently corrupted every away-team zone-based statistic.
2. **Rally/Action timestamps were rally-relative, not match-absolute.** `Rally.video_t_start`/`video_t_end` were never populated (always `None`), and every `Action.video_t_start` reset to the same ~0–12 second window on every rally, so a multi-set match's 200+ rallies all claimed to happen in the match's first 12 seconds. Fixed by threading a running `match_clock` through `_simulate_set`/`generate_synthetic_match` (generator stays pure and rally-relative internally, per its own docstring) and having `persistence.py` add each rally's match-clock offset when writing `Action.video_t_*`. A first fix attempt that threaded the offset directly into the generator's action-chain builder was caught as introducing a *new* inconsistency (ball-position timestamps would go absolute while player-position timestamps stayed rally-relative) and reverted before landing. Verified: timestamps now span the real ~1251-second match and are strictly non-overlapping rally-to-rally.
3. **Migration 0002 read live ORM metadata at migration-run time instead of freezing DDL.** See the revised decision above — this was the largest single fix.
4. **Provenance was not enforced at the schema level, contrary to `DATA_FLOW.md`'s "every prediction must link model_version, weights_hash, dataset_version."** `Action.model_run_id` was nullable with `ON DELETE SET NULL`, inconsistent with `BallObservation`/`PlayerObservation` (already correctly non-nullable/`CASCADE`) and inconsistent with this ADR's own "no generic Prediction table" decision, which only holds if every prediction row *always* carries its provenance. Fixed: `Action.model_run_id` is now `NOT NULL` with `ON DELETE CASCADE`. `Rally`/`Phase` also gained nullable `model_run_id`/`confidence` columns they previously lacked entirely — nullable is correct for those two (a rally or phase can be defined by rule-based/manual means with no single model run behind it), but the columns now exist so Phase 6's real rally/phase detectors have somewhere to record provenance instead of that being an afterthought.

**Should-fix, addressed in this pass:**

- **S1 (partial): no uniqueness on ordering columns.** `MatchSet.index`, `Rally.index_in_set`, `Phase.index_in_rally`, and `Action.index_in_phase` had no DB-level constraint preventing two siblings from claiming the same position under one parent. Added `UniqueConstraint`s (`uq_set_match_index`, `uq_rally_set_index`, `uq_phase_rally_index`, `uq_action_phase_index`). **Not addressed:** `persist_synthetic_match` still creates a fresh `Season`/`Team`/`Player`/`Roster` row on every call rather than get-or-create, so repeated demo generation accumulates duplicate `Team` rows for the same team name — tracked in `TECH_DEBT.md` rather than fixed here, since it's a persistence-layer design change orthogonal to the schema-freezing work this pass focused on.
- **S2: the lineage helper (`lineage.py`'s `explain_metric`) is not actually callable end-to-end by any real caller** — the statistics engine doesn't return the contributing `Action` ids a real explanation would need to chain back through `Rally`/`Phase`/`Video`. Not fixed in this pass; documented in `TECH_DEBT.md` as a real gap rather than left silently implied to work because it has passing unit tests (which exercise it with hand-built ids, not output from the real engine).
- **S3: `Video.video_hash` was globally unique, not org-scoped.** Two different clients uploading byte-identical footage (e.g. a shared vendor highlight reel) would collide across tenants. Fixed: replaced the column-level `unique=True` with a table-level `UniqueConstraint("organization_id", "video_hash")`.
- **S4: this ADR and related docs said "Phase 3" in two places that actually meant Phase 5** (court calibration, and "when a real CV pipeline first creates a non-synthetic `PipelineRun`") — Phase 3 is the frontend design-system phase; Phase 5 is the first real CV pipeline phase per `ROADMAP.md`. Both corrected above and in `TECH_DEBT.md`.

## What was verified (not just written)

Every module here has real, passing tests, several of which caught actual bugs during development rather than confirming what was already believed correct:

- `court.py`: 12 geometric tests (mirror is its own inverse, zone anchors are point-symmetric, `nearest_zone` round-trips).
- `stats/engine.py`: 27 known-input/known-output tests per statistic, including the classic SDHSAA worked example.
- `lineage.py`: 4 tests including the exact "43% → 21 events → 21 rallies → clips" scenario from the project's own spec.
- `corrections.py`: 4 tests against a real (SQLite) database proving the append-only guarantee holds in practice — a correction never mutates a prior `HumanCorrection` row, and the original prediction's provenance survives a correction being applied.
- `synthetic/persistence.py`: 7 tests against real SQLite proving the full generator → persistence pipeline produces a coherent graph (right row counts, no cross-team phase contamination, in-bounds coordinates, match-absolute non-overlapping timestamps, deterministic row counts for a repeated seed).
- `services/worker`: a new test proves the worker task leaves real ontology rows behind (not just the JSON blob), and a second proves Celery redelivery does **not** duplicate `MatchSet`/`Action` rows — the specific risk the "one transaction" design decision above exists to prevent.
- `services/api`: 7 new tests exercise the read endpoints (`/sets`, `/rallies`, `/rally/{id}/actions`, `/statistics`) against real persisted data end-to-end, including that every one of them is genuinely org-scoped (a cross-tenant request 404s) — the exact property an earlier independent review (ADR-002/ADR-003's Phase 1 review) flagged as the single most security-critical thing to get right in this codebase.

Two real design gaps were caught and fixed *during* this implementation, not after: the `PipelineRun.video_id NOT NULL` conflict with synthetic runs (see above), and an SQLAlchemy relationship needed between `Action`/`Outcome` after an initial draft tried to bolt an `outcome` attribute onto `Action` dynamically (a pattern that would have silently worked but bypassed proper typing and eager-loading) — replaced with a real `relationship(..., uselist=False)` pair plus `selectinload` in the route that needs it.

## What remains unverified

Everything that needs a live Postgres: the migration has only been checked via `alembic upgrade head --sql` (offline), never applied to a real database. Consistent with the same limitation ADR-002/ADR-003 already documented for this sandbox — not new, but still open.

## Consequences

- `packages/domain-py` is now the largest package in the repo by a wide margin (23 tables, a statistics engine, a lineage helper, a correction service). Splitting `ontology.py` further (e.g. by entity family) is reasonable once it grows past this session's scope — not yet, per "no abstracciones antes de que se necesiten."
- The JSON-blob/ontology dual-write in the worker task is real, temporary complexity with a clear removal condition (Phase 3's frontend migrating off the blob) — tracked in `TECH_DEBT.md`, not left implicit.
- Every future API route touching `Rally`/`Action`/`MatchSet` must repeat the join-through-`Match` org-scoping pattern `api/routes/ontology.py` establishes — there is no shortcut (no `organization_id` column on those tables, by design, since they don't need one for anything except this).

## Revisit triggers

Phase 3's Match Analysis UI is built against the new `/sets`/`/rallies`/`/statistics` endpoints — remove the JSON-blob write path once nothing reads it. A real CV pipeline (Phase 5+) produces its first non-synthetic `PipelineRun` — revisit the `video_id` nullability exception at that point (confirm application code enforces the synthetic-only nullability in practice, add a DB-level constraint if the risk of a real pipeline run slipping through with a null `video_id` becomes non-theoretical). Court calibration is implemented (Phase 5) — add the deferred `CourtCalibration` table then, not before. `persist_synthetic_match` gets a second caller or the demo is regenerated repeatedly in one environment — switch `Season`/`Team`/`Player`/`Roster` creation to get-or-create before duplicate rows become a real UI problem. The statistics engine's action-level output is consumed by anything that needs per-metric drill-down — wire `lineage.py`'s `explain_metric` to real contributing-action ids at that point.
