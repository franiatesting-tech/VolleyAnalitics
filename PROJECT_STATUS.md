## Continuation session 2026-08-30: bug fixes and hardening after picking up the goldset/annotation groundwork above

This session picked up mid-Phase-4/5 (real footage acquired, `golden-v0` frozen, `ml/` core and professional annotation protocol already built) and did a full-repo health check (ruff, pyright, and every package's test suite — all green baseline confirmed) before making changes. Four real, previously-tracked issues fixed, all with new regression tests, all suites re-confirmed green after each:

1. **`leakage_safe_split` reshuffle bug, fixed before it could ever bite `golden-v0`.** The split algorithm's greedy fill reassigned most of an existing frozen split whenever the dataset grew (reproduced: 10 videos → add 2 more, 8 of the original 10 moved splits). Added an `existing_assignment` parameter that pins every already-assigned group to its prior split; `split_cli.py` gained a matching `--existing` flag; `docs/datasets/README.md` now documents it as required reading before `golden-v0` → `golden-v1`. `golden-v0` itself needed no correction (it's only been split once so far), but every future growth must pass `--existing golden-v0/generated/split.json` or risk silently invalidating any evaluation already run.

Added `ModelRunStage.INGEST`; `ingest_video` now creates one `PipelineRun`+`ModelRun` row per successful ingest, `config_hash`-fingerprinted against the actual ffmpeg binary's own `configuration:` string (two different builds probing identical bytes now produce distinguishable provenance — verified by a dedicated test). This was the entry's own stated blocker for "before real annotation work begins on real footage," which is now imminent for `golden-v0`.
3. **Game-logic bug: `AttackStats.blocked` and `BlockStats.block_kills` were structurally unreachable on synthetic data.** Both formulas were individually correct and individually unit-tested, but the generator never produced a rally ending in an opposing block stuffing an attack, so neither statistic could ever be nonzero — flagged by an earlier independent domain review as "real but never exercised," left unfixed at the time. ## Phase 4 independent review: 3 blocking security vulnerabilities found, fixed, and independently re-confirmed closed

Two independent reviews ran in parallel (architecture-lead + security-privacy-license-reviewer, neither aware of the other's findings), then this session fixed what they found and re-verified live.

**architecture-lead verdict**: *"Sound enough to build Phase 5 on, conditional on B-1 and B-2."* 2 blocking, 6 should-fix.

**security-privacy-license-reviewer verdict**: ***"FAIL — not acceptable to ship as-is."*** 3 blocking (all empirically demonstrated with real exploits, not theoretical), 3 high, 8 medium, several low/notes.

### Blocking, all fixed 2026-08-30

**From architecture-lead:**
1. **A `Video` could get stuck in `VALIDATING` forever**: `complete_video_upload` committed the status flip before calling `enqueue_ingest_video`; if enqueueing then failed, the row was stuck (idempotency guard blocked any retry from actually re-enqueueing). **Fixed**: enqueue wrapped in try/except, reverts to `FAILED` (not idempotency-guarded) on failure so a retry genuinely retries. Also added an `object_exists` check before enqueueing at all, closing a related "enqueue a task that will always fail because nothing was uploaded" gap.
2. **No PTS mapping or frame dimensions captured**, contrary to `DATA_FLOW.md`'s explicit "never key anything by frame number alone" requirement — every downstream ground-truth timestamp would have been computed as `frame_index / avg_frame_rate`, wrong for variable-frame-rate sources and silently offset for non-zero-`start_time` containers (e.g. MPEG-TS). **Fixed**: `VideoProbeResult`/`probe_video` now extract `width`, `height`, `start_time_seconds`, `time_base`; new `Video` columns (migration `0004`, applied to the live Postgres); `ingest_video` persists them.

**From security-privacy-license-reviewer (the severe ones):**
1. **Unauthenticated cross-org write via a forged upload token**: `LOCAL_STORAGE_SIGNING_SECRET` defaulted to a hardcoded string checked into source/git history, and nothing prevented `STORAGE_BACKEND=local` (or that default secret) from reaching a real environment. Demonstrated live: a forged token with no `Authorization` header wrote to another org's storage key. **Fixed**: new startup guards in both `services/api`/`services/worker`'s `Settings` (`_local_storage_cannot_reach_production`) crash immediately if `ENV` is outside dev/test and either the local backend or the default secret is still in play. Re-verified live post-fix: the exact same forged-token attack, replayed against the rebuilt containers, now gets `403` (the deployment's real secret is no longer the public default).
2. **Cross-org video read via ffprobe following attacker-controlled file references**: an uploaded `.m3u8` HLS playlist referencing `../../../other-org/video.ts` made ffprobe read and report another organization's video metadata — demonstrated live. **Fixed**: `probe_video` now refuses to process any file whose first 256 bytes look like printable text (real binary video containers never do; HLS/concat/similar reference formats are text) before ffprobe ever sees it, plus `-protocol_whitelist file` as defense in depth. New regression tests pass, including one using the reviewer's own exact attack payload.
3. **Unbounded memory/disk-fill DoS**: the local-upload route buffered an entire request body with no size limit — a 25 MiB PUT succeeded with no check at all. **Fixed**: a 512 MiB cap enforced during streaming, rejecting with `413` as soon as exceeded.

### High, all fixed or resolved 2026-08-30

- **Signed token replay / content-swap TOCTOU**: the same (key, token) pair could be PUT twice with different content after the first was already hashed, detaching `video_hash` from what's actually stored. **Fixed**: first-write-wins — `local_upload` now rejects with `409` if the object already exists.
- **FiftyOne/MLflow exposed unauthenticated on every network interface**, with FiftyOne mounting every organization's uploaded video read-only and no auth of its own. **Partially fixed**: both services' ports now bind to `127.0.0.1` only, not `0.0.0.0`, closing the network-reachable version of the gap. The underlying "no per-org access control at all" limitation is real and honestly tracked in `TECH_DEBT.md` (not silently dropped) — acceptable for today's solo-local-dev-against-synthetic-data reality, must be revisited before this tooling ever runs anywhere real client video exists.
- **FFmpeg license mislabeled**: the pinned build is actually **LGPL-3.0**, not LGPL-2.1+ as originally recorded (`--enable-version3` is set) — caught by extracting the configuration string directly from the binary and cross-checking the release tarball's own `LICENSE.txt`, not trusting the build's self-report alone. **Escalated to the user per CLAUDE.md's legal-risk trigger** (this is exactly the kind of decision this project's rules say must go to the user, not be resolved unilaterally): asked whether the worker image is ever distributed to a third party. **Answer: never — hosted-SaaS only.** Under that confirmed model, LGPLv3's stricter obligations (which apply to *distribution*, not hosting) don't require disclosing this project's proprietary source, so D-006 remains closed on that basis — but must be reopened if the deployment model ever changes. `LICENSE_DECISIONS.md`/`OSS_MANIFEST.md` corrected to LGPL-3.0-only with the full reasoning recorded. Two hygiene gaps (the pinned build's own `LICENSE.txt` wasn't preserved in the deployed image; `THIRD_PARTY_NOTICES.md` not regenerated) — the first is now fixed (`infra/scripts/install-ffmpeg-lgpl.sh` preserves it), the second remains tracked in `TECH_DEBT.md`'s existing entry.

### Medium, fixed 2026-08-30

Worker trusts `storage_key` with no org cross-check (fixed: `ingest_video` now asserts it matches the video's own org); unhandled-exception 500s with info leakage on a malformed `expires_at` or a traversal-attempt key (fixed: both now map to clean `403`s); `complete-upload` never checked an object was actually uploaded before enqueueing (fixed: `object_exists` check added, `409`s otherwise); unvalidated `content_type` was a stored-XSS-via-signed-URL vector once R2 is fronted by a public domain (fixed: `VideoUploadRequest.content_type` now allowlists real video MIME types via a Pydantic validator).
